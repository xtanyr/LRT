## Требования и реализованная цепочка

Основание — [раздел 07 ТЗ](<C:/LRT/roadmap documentation/07_admin_panel_and_triggers.md:56>) и относящиеся к ИПВ части разделов 04, 06, 08 и 12. В начале раздела 07 осталась старая таблица T1 = 4; окончательное согласованное значение ниже в том же документе — **3 месяца**.

| Условие | Окончательное требование | Реализация |
| --- | --- | --- |
| T1 | Три месяца подряд рейтинг < 60; любое повышение внутри окна отменяет срабатывание | Есть |
| T2 | Двенадцать месяцев подряд рейтинг < 80; повышение не отменяет срабатывание | Есть |
| T3 | Одна и та же метрика в красной зоне три месяца подряд | Есть, сохраняется metricId |
| Стаж | Минимум шесть месяцев на кофейне и после утверждения | Есть, но пропуск не объясняется пользователю |
| ИПВ | Не начат → В работе → Завершён; при начале убрать активное уведомление | Есть API и экран |
| Просрочка | Визуальный акцент после 14 дней без автоматической эскалации | Есть в дашборде и списке |
| Настройки | Пороги, месяцы, стаж и активность редактируются через интерфейс | Только API; редактора нет |
| Ручное исключение | Установка/снятие флага с причиной; подавление уведомлений и индикаторов | Только API; существующие события не подавляются |

[Правила](C:/LRT/backend/src/ipv-triggers/trigger-rules.ts:5) проверяют отправленные отчёты и сохранённые результаты рейтинга. [Монитор](C:/LRT/backend/src/ipv-triggers/trigger-monitor.service.ts:10) зарегистрирован в приложении и выполняется каждые 15 минут. При совпадении он сохраняет статус ИПВ и уведомления назначенным лидерам города. Уведомления COO отдельно ТЗ не требует.

Окно заканчивается предыдущим календарным месяцем: на 05.10.2026 T1/T3 проверяют июль–сентябрь, T2 — октябрь 2025–сентябрь 2026. Выбор месяца на экране это окно не меняет. После сохранения/отправки отчёта монитор не вызывается немедленно; это задержка текущей реализации, а не явно запрещённое ТЗ поведение.

## Что мешает пользоваться функционалом

1. **Завершённые и будущие назначения учитываются как действующие.** Монитор загружает все назначения без проверки их дат. Затем любой лидер с исключением, пустой датой утверждения или недостаточным стажем блокирует всю кофейню через `leaders.some(...)`. Историческое назначение способно подавить проверку текущего подходящего лидера. [Загрузка и проверки](C:/LRT/backend/src/ipv-triggers/trigger-monitor.service.ts:13).

2. **Пустая дата утверждения исключает все триггеры без объяснения.** `monthsOld(null, 6)` возвращает false. Базовый seed эту дату не задаёт, миграция только добавляет nullable-поле. Само требование шестимесячного стажа верно; проблема в отсутствии объяснения и в тестовых данных. Даты можно заполнить в управлении пользователями. [Проверка](C:/LRT/backend/src/ipv-triggers/trigger-rules.ts:25), [форма пользователя](C:/LRT/frontend/src/pages/admin/AdminUsersPage.tsx:168).

3. **Настройка правил через интерфейс отсутствует.** Вкладка только выводит код, порог и число месяцев. Нет полей стажа, активности, редактирования или сохранения. Поэтому предложение в инструкции UAT временно уменьшить окно T2 сейчас через интерфейс невыполнимо. [Вкладка](C:/LRT/frontend/src/pages/admin/AdminConfigPage.tsx:87), [API изменения](C:/LRT/backend/src/ipv-triggers/ipv-triggers.service.ts:10).

4. **Ручные исключения недоступны пользователю.** Frontend не использует API исключений. Установка флага через API останавливает новую генерацию, но уже созданные уведомления и колокольчики продолжают отображаться: чтение статусов/дашборда не подавляет их по активному флагу. [Исключения](C:/LRT/backend/src/ipv-triggers/ipv-triggers.service.ts:52), [чтение дашборда](C:/LRT/backend/src/dashboard/dashboard.service.ts:15).

5. **Причина срабатывания показана неполно и местами неправильно.** T3 описывается как «Рейтинг < 0», хотя проверяет красную метрику. В списке и карточке нет даты срабатывания и названия конкретной метрики T3, требуемых ТЗ. [Экран и описание правил](C:/LRT/frontend/src/pages/city-leader/CityTriggersPage.tsx:120).

6. **Карточка одной кофейни получает триггеры других кофеен.** Frontend передаёт `coffeeShopId` в query, backend его не принимает; дополнительной фильтрации ответа на странице нет. [Запрос](C:/LRT/frontend/src/pages/city-leader/CityShopPage.tsx:66), [контроллер](C:/LRT/backend/src/ipv-triggers/ipv-triggers.controller.ts:34).

7. **Ошибка загрузки выглядит как отсутствие событий.** На странице нет сообщения об ошибке GET списка; после отказа запроса отображается «Нет триггеров». Ошибка загрузки конфигурации подменяется пустым списком. Неудачные действия изменения статуса также не объясняются. [Загрузка и действия](C:/LRT/frontend/src/pages/city-leader/CityTriggersPage.tsx:39).

Дополнительные ограничения: правила создаются отдельным seed, а не миграцией; без seed монитор получает пустую конфигурацию. При одновременных совпадениях сохраняется первое правило, поскольку любое незавершённое ИПВ подавляет остальные; явный приоритет конфигураций не задан. Требование выбора единственного правила в ТЗ не найдено — это требует согласованной трактовки, а не признания отсутствующим движком.

## Проверка локальных данных и воспроизведение

В локальной базе три активных правила с параметрами 3/12/3 и стажем 6/6, 48 отправленных отчётов, ни одного ИПВ. У Coffee Shop 1 два активных назначения: одно с датами 01.01.2026, второе — с назначением 16.09.2026 и пустой датой утверждения. Второе назначение блокирует всю кофейню.

| Кофейня | Июль → август → сентябрь 2026 |
| --- | --- |
| Coffee Shop 1 | 86 → 94 → 98 |
| Coffee Shop 2 | 72 → 80 → 84 |
| Coffee Shop 3 | 91 → 99 → 100 |
| Coffee Shop 4 | 64 → 72 → 76 |

В этих трёх месяцах нет критичных метрик. Поэтому текущие demo-данные сами по себе не должны вызвать T1/T3. Для T2 не хватает октября–декабря 2025. Это состояние локального Docker, а не подтверждение состояния сервера.

Настоящий монитор из локального контейнера проверен с адаптером базы в памяти — соединения и записи в БД не выполнялись:

| Сценарий: отправленные рейтинги 50 → 50 → 50, подходящий стаж | Создано событий / уведомлений |
| --- | --- |
| Только действующий подходящий лидер | 1 / 1 |
| Добавлено завершённое назначение с пустой датой утверждения | 0 / 0 |
| У действующего лидера пустая дата утверждения | 0 / 0 |

Существующие тесты правил: **4 прошли**. Два выбранных теста редактирования истории: **2 прошли**, остальные пропущены. Они подтверждают, что при `ALLOW_HISTORICAL_REPORT_EDITING=true` редактирование demo-отчётов за июль/август сохраняет новый рейтинг, который затем читает монитор. Все интерфейсные тесты не запускались.

Для импортированных отчётов есть отдельный разрыв подготовки данных: форма отправляет `sourceSheet`, `fields`, `importSource` из formData, а сохранение ожидает числовые поля и две ссылки; такой запрос отклоняется до обновления рейтинга. [Импорт](C:/LRT/backend/src/imports/import.service.ts:190), [валидация сохранения](C:/LRT/backend/src/reports/reports.service.ts:74). Этот случай проверен по коду, отдельно в базе не воспроизводился.

## Порядок исправления

Сначала исправить выбор действующих назначений и показать причины исключения из мониторинга. Затем добавить редактор правил и управление ручными флагами; согласовать подавление уже существующих индикаторов. После этого исправить фильтрацию по кофейне и объяснение T1/T2/T3, добавить обработку ошибок. Проверять реальный монитор, создание ИПВ, уведомление и переходы статусов на подготовленной последовательности отправленных отчётов. Для диагностики сервера нужны его фактические назначения, даты, настройки и рейтинги; автоматически менять эти данные или подставлять даты нельзя.
