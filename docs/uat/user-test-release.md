## Что делает одноразовая подготовка

Удаляет отчёты и их анализ, тестовые аккаунты, назначения, комментарии, аудит, уведомления, события ИПВ, токены восстановления и старые города/кофейни. Сохраняет выбранного администратора, метрики и пороги, вопросы анализа, категории/переопределения порогов, правила триггеров, цвета и системные настройки. Отсутствующие базовые настройки добавляет без перезаписи существующих.

Загружает справочник [из предоставленной таблицы](https://docs.google.com/spreadsheets/d/17WoVOSMYF07C7biGVmgX7v3_0OaQ0U_6ZwmqRym3bp8/edit?gid=113237269), снятый 12.10.2026: Омск — 18, Москва — 16, Казань — 11, Санкт-Петербург — 5, Нижний Новгород — 4, Новосибирск — 8, Самара — 6. Всего 7 городов и 68 кофеен. Нумерация и строки «Всего» исключены; названия сохранены.

Команда работает один раз. Маркер в базе блокирует повторную очистку и запуск старых демонстрационных seed-команд. Контейнер API при обычном старте выполняет только `prisma migrate deploy`; сидирование не запускается автоматически. Постоянный том `lrt_postgres` хранит данные между пересборками контейнеров.

## 1. Обновить проект

После переноса актуальных изменений в репозиторий на сервере:

```bash
cd ~/lrt
git pull
sudo docker compose -p lrt up -d --build api web
sudo docker compose -p lrt ps
```

Сохраните серверный `.env` и его `HTTP_PORT`: существующая схема с NPM/host Nginx не меняется. Для обычного режима установите `ALLOW_HISTORICAL_REPORT_EDITING=false`. На время регистрации участников включите `ALLOW_SELF_REGISTRATION=true`: они создают аккаунт с именем и своим паролем на `/register`, затем администратор назначает роль, кофейню или город. Без назначения доступ к чужим отчётам закрыт. Когда все зарегистрируются, регистрацию можно отключить; существующие аккаунты продолжат работать. После изменения `.env` пересоздайте API: `sudo docker compose -p lrt up -d --force-recreate api`.

Если в сценарии тестирования триггеров нужно заполнять старые месяцы, временно установите `ALLOW_HISTORICAL_REPORT_EDITING=true`; после этого сценария верните `false`. Импортированные исторические отчёты остаются защищены от редактирования.

## 2. Предпросмотр без удаления

```bash
sudo ADMIN_EMAIL=sofyalav2004@gmail.com bash deploy/ubuntu/prepare-user-test.sh
```

Проверьте выбранного администратора, количество удаляемых записей и итоговый справочник. При отсутствии ADMIN с этим email или некорректном справочнике команда остановится без изменения данных. После выполненной подготовки обычный предпросмотр остаётся доступным и показывает `alreadyPrepared: true`, `canApply: false`; повторное применение будет отклонено.

## 3. Очистка и однократное сидирование

```bash
sudo ADMIN_EMAIL=sofyalav2004@gmail.com bash deploy/ubuntu/prepare-user-test.sh --apply
sudo docker compose -p lrt ps
curl -fsS https://lrt.scr-tech.ru/api/health
```

Скрипт сначала выполняет проверку `--require-ready` без изменения данных: проверяет домен, администратора, справочник и отсутствие маркера подготовки. Ошибка этой проверки, в том числе попытка повторного применения, останавливает команду до остановки сервисов. Затем скрипт останавливает API/web, сохраняет дамп PostgreSQL в `~/lrt/backups/`, проверяет его список содержимого и записывает контрольную сумму, применяет подготовку транзакцией и запускает API/web. При ошибке резервного копирования очистка не запускается; при ошибке транзакции изменения откатываются. В обоих случаях сервисы запускаются снова. Путь к резервной копии выводится в терминал.

После очистки ожидается один пользователь ADMIN, 7 городов, 68 кофеен и отсутствие отчётов, назначений и уведомлений. Участники регистрируются, администратор проверяет аккаунты, назначает лидерам кофеен точки с датой начала и лидерам городов города; COO получает доступ ко всем городам.

Не используйте `docker compose down -v`, `prisma migrate reset`, `db push --force-reset` или старый demo seed для обновления рабочего стенда.

## 4. Дальнейшие обновления

```bash
cd ~/lrt
git pull
sudo docker compose -p lrt up -d --build api web
```

Команду подготовки повторять не нужно. Все созданные пользователями данные и изменения справочников останутся в базе.

## Проверка перед приглашением

1. Войти сохранённым ADMIN; проверить города, кофейни, метрики и вопросы анализа.
2. Зарегистрировать три аккаунта участников, указать имена; администратором назначить роли LEADER, CITY_LEADER и COO, кофейню и город. Лидер города видит только назначенный город.
3. У лидера заполнить доступный месяц, дождаться автосохранения, обновить страницу, сверить значения/цвета, отправить отчёт.
4. Проверить этот отчёт и автора у CITY_LEADER и COO; сверить месячный/годовой рейтинг и среднее города.
5. Изменить значение метрики и текст анализа, проверить аудит; деактивировать и активировать тестовую кофейню.
6. Открыть основные экраны с телефона; проверить меню, выбор месяца и модальные окна с клавиатуры.
7. Проверить выход и повторный вход; уведомления и ссылки не должны вести к несуществующей кофейне.

Восстановление пароля требует настроенной почтовой доставки (`PASSWORD_RESET_EMAIL_API_KEY`, `PASSWORD_RESET_FROM_EMAIL`), Google-вход — OAuth credentials. До их настройки используйте вход по email/паролю; участники задают пароль при регистрации. В интерфейсе администратора нет создания аккаунтов или смены чужого пароля.
